# Механика
Управление автомобилем. 
## Управление
WASD - газ, тормоз, повороты
Shift - сцепление (использовать не обязательно)
Space (зажать) - ручной тормоз
Мышь - осмотр

## Детали
Реализована трансмиссия (двигатель -> МКПП -> колёса)
Двигатель имеет звуки
Колёса имеют звуки (трение шин)
Ввод с клавиатуры фильтруется, сглаживается и интерпретируется в соответствии с условиями, для удобства управления:
- сцепление контролируется АВТОМАТИЧЕСКИ
- передачи переключаются АВТОМАТИЧЕСКИ
- руль выворачивается на "безопасный" угол на большой скорости АВТОМАТИЧЕСКИ
- машина плавно стартует используя сцепление АВТОМАТИЧЕСКИ (при нажатии на газ)
- при намерении поехать назад с места газ с тормозом (интерпретация W и S соответственно) меняются АВТОМАТИЧЕСКИ

# Краткое описание архитектурных решений и встраивания новой логики
## 1. Загрузка уровня
UI представляет собой экран, который открывается и работает на основе существующей механики UIController & компания. А значит, он автоматически доступен на любой сцене игры, т.к. UIController гарантировано появляется как часть ProjectContext.

## 2. Машинка
```Scripts/Gameplay/Car```
Использовал MVP: файлы в основном лежат в соответствии с расшифровкой аббревиатуры, за исключением ввода: там это целая система из получения и обработки нажатия клавиш (фильтры, ассистенты и т.п.) - поэтому вынес в отдельную папку. По факту - представляют из себя View
Ещё одно отступление - конфиги, которые хранятся в отдельной директории и работают на основе ScriptableObject.
Мотивация для использования этого паттерна следующая: хотелось максимально отделить моделирование физических процессов автомобиля от непосредственного их применения. По большому счёту, взаимодействие с движковым API можно рассматривать как И отображение модели, И передачу данных в модель (считывание скорости, кол-во оборотов колёс в минуту и т.п.), поэтому взаимодействие с WheelCollider'ами и AudioSource'ами происходит во View. Использованный в Core MVC в такой ситуации в чистом виде здесь подходит хуже, т.к., опять же, если говорить про классический MVC, это выглядело бы как Controller, хранящий ссылки на ВСЁ, передающий UserInput и данные физики в модель, и View, хранящий ссылки на это же ВСЁ, интерпретирующий посчитанные данные. Получался бы лютейший дубляж кода. 
А в целом, для такой достаточно массивной и сложной механики, MVP хорош тем, что его потенциально легко тестировать, и легко горизонтально расширять (например, в существующую систему будет достаточно легко интегрировать поведение ботов, которые будут по факту просто дёргать API модели, а сами из себя будут представлять View наследника от IInputSource.
На более высоком уровне (директория Gameplay), использовано разделение на фичи. Применение многоуровневого подхода позволяет:
- не теряться среди бесконечного количества, например, Presenter'ов от фичи к фиче, если бы всё было сброшено в одну папку, т.е. это оптимизирует вертикальное расширение
- использовать разные подходы для разных фич, чтобы сделать процесс разработки и поддержки максимально оптимальным (что уже сделано, если сравнить код машинки и код тряски камеры)

Машинка как префаб имеет свой GameObjectContext - что позволяет использовать несколько машинок на сцене, которые сами по себе работают изолированно. UI в свою очередь имеет доступ только к одной машине - к той, которая помечена как машина игрока, для этого на уровень контекста сцены вынесен так называемый регистр машины игрока.

### 2.1 Камера
Управление и эффекты реализованы без кода на основе Cinemachine

# Известные проблемы
- При старте колёса испускают звук пробуксовки - баг WheelCollider (скорее всего - не хватает суб-шагов симуляции)
- Симуляция сцепления примитивная - связано с ограниченным API WheelCollider (физически нет возможности получить т.н. "feedback torque")
